## 提示词 1：需求发散

```text
你是 Codex，以资深产品经理和软件工程负责人的身份参与一个单人课程项目。

项目为“青禾流转”，面向高校师生的校园物品共享、二手交易、免费赠送、绿色回收和公益物资流转平台。技术实现由 Codex 设计，后续由 WorkerBuddy 编码，开发时间约 4 周。

请先不要限定最终范围，输出一份功能尽量完整但不过度企业化的原始需求文档：
1. 按角色、使用场景、功能、优先级组织；
2. 每条功能说明业务价值和采用理由；
3. 覆盖借还、出售、赠送、回收、交接、取消、逾期、争议和公益异常；
4. 包含多高校隔离、单一高校、多校区、学生名单核验和三类角色；
5. 支付、短信和全国高校认证允许模拟；
6. 只写业务需求，不写数据库表、代码框架或接口实现；
7. 单列高级但可选的功能，供后续人工删减。
```

## 提示词 2：范围删减

```text
基于 Codex 的原始需求文档，进行人工范围收敛。

项目约束：
- 单人开发，约 21 个工作日；
- Flask + Jinja2 + PostgreSQL；
- Web-only，基础响应式；
- 四类物品流转必须完整可操作；
- 公益首版只做实物捐赠、项目目标和进度、回执公示；
- 公益义卖只做总体设计，不进入首版；
- 不接真实支付、短信、政府身份接口、地图和物流；
- 多高校逻辑隔离，同校跨校区允许，跨学校禁止；
- 三类可见角色；
- 需要学生名单注册核验、模拟短信、图片上传、头像和角色标签。

请输出删减决策表，逐项标记保留、简化、延后或删除，并给出原因。不得新增原始需求中没有依据的大模块。
```

## 提示词 3：需求收敛

```text
根据保留后的范围，整理正式需求规格说明书。

要求：
1. 严格按删减决策表的范围，不增加新功能；
2. 每条需求有唯一编号、业务规则、前置条件、主流程、异常路径和验收结果；
3. 明确同一物品同一时间只能存在一个进行中的流转；
4. 覆盖取消、拒绝、逾期、归还、损坏、争议和模拟支付失败；
5. 覆盖跨学校越权和同校跨校区合法访问；
6. 覆盖公益募集不得超募、实物核验和回执；
7. 输出角色-功能矩阵、用例图和流程图；
8. 使用统一术语，AI 名称统一为 Codex。
```

## 提示词 4：闭环复核

```text
请以软件工程评审者身份检查“青禾流转”6.1 需求：
- 是否清晰说明谁发起、谁处理、何时结束；
- 正常流程与失败、取消、超时、重试、越权是否闭环；
- 页面描述与业务状态和数据记录是否一致；
- 是否存在真实资金、真实短信或外部审批依赖；
- 是否存在多人协作才能完成的功能；
- 是否仍能在 21 个工作日内实现和测试。

只报告会导致需求不可实施、业务不闭环或范围失控的问题，并直接修订文档。
```
