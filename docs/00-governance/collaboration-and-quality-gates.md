# 青禾流转开发与质量门禁

## 1. 开发角色

| 角色 | 责任 |
|---|---|
| 项目维护者 | 范围审批、设计、实现、安全审查、发布和最终验收 |
| 评审者 | 独立检查需求符合性、测试证据、隐私和发布风险 |

个人开发时仍要执行“实现”和“验收”两个独立步骤：完成功能后重新阅读需求和设计，再运行测试和公网检查，不能只凭开发时印象宣布完成。

## 2. 单写入者规则

- 同一批文件同一时间只由一个开发者修改。
- 合并或交接使用固定 commit。
- 代码审查和发布验证期间，停止无关联的功能修改。
- 发现设计矛盾时先更新需求和决策记录，再改代码。

## 3. 质量门禁

### G0：需求与设计基线

- 范围、角色、验收标准、数据边界和排除项已明确。
- 关键技术选型有可行性依据。
- 没有依赖未确认的账号、付费服务或外部审批。

### G1：基础骨架

- 应用可启动，数据库可初始化。
- 配置缺失时给出可操作错误。
- 基础鉴权、权限和测试框架可运行。

### G2：第一条业务闭环

- 第一条完整流转链从创建到结束可用。
- 正常、失败、取消、越权和高校隔离路径有测试。
- service 接口、状态机、事务与设计一致。
- 同一模式稳定后才扩展到其余业务。

### G3：全功能完成

- 四类物品流转、公益首版、管理端和图片上传完成。
- 单元、集成和验收测试通过。
- 已知限制、设计偏差和安全问题已记录。

### G4：发布候选

- 数据库迁移演练完成。
- Preview smoke 和公网 smoke 通过。
- 回滚方案、密钥管理、隐私边界和运行监控可执行。
- 无阻断缺陷后才能发布。

## 4. 变更边界

- 小范围接线、权限、状态机、事务和部署适配问题可以直接修复，并补回归测试。
- 新增核心模块、重做数据库结构或改变业务规则前，先更新需求、设计和决策记录。
- 测试证据不可复现时，不能以“本地看起来正常”替代。

## 5. 测试证据

每次门禁至少保存：

- commit hash；
- Python 和依赖版本；
- 测试命令；
- 实际输出；
- 失败项与修复说明；
- 使用的数据库和环境；
- 页面截图或 smoke test 结果（适用时）。

通过结论以可复现证据为准。
