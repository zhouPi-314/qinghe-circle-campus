# 青禾流转协作与质量门禁

## 1. 角色

| 角色 | 责任 |
|---|---|
| 用户 | 范围批准、重大变更批准、最终业务验收、发布批准 |
| Codex | 6.1 需求、6.2 设计、统一标准、独立验收、安全审查、受控修复、发布门禁 |
| WorkerBuddy | 6.3 编码、单元测试、集成测试、缺陷修复和实现记录 |

WorkerBuddy 是主要实现者。Codex 不参与日常功能编码。

## 2. 单写入者规则

- WorkerBuddy 开发期间只有 WorkerBuddy 修改业务代码。
- Codex 验收期间 WorkerBuddy 暂停业务代码编辑。
- Codex 与 WorkerBuddy 不同时修改同一批文件。
- 交接使用固定 commit；交接后新增修改必须标明来源。

## 3. 强制门禁

### G0：交接确认

触发：6.2 设计获批、准备进入 6.3。

WorkerBuddy 必须：

- 阅读 `AGENTS.md`、工程标准、术语、6.1、6.2 和交接文档；
- 提交实施确认；
- 列出需要澄清的问题；
- 停止，不写业务代码。

通过条件：用户或 Codex 书面确认无阻塞问题。

### G1：基础骨架

触发：项目可启动、PostgreSQL 可初始化、基础鉴权可用。

WorkerBuddy 必须停止并提供：

- 固定 commit；
- 启动命令和结果；
- 数据库初始化结果；
- 基础权限测试；
- 当前目录结构；
- 与设计不一致项。

Codex 检查：目录、依赖、配置、模块接口、数据库连接和基础安全。

通过后才能扩展业务模块。

### G2：第一条业务闭环

触发：第一条完整流转链完成。

WorkerBuddy 必须停止并提供：

- 从创建到结束的完整流程；
- 正常与异常测试；
- 权限与高校隔离测试；
- commit 和测试日志；
- 对共享模式、状态和 service 接口的实现说明。

Codex 检查：状态机、事务、接口、错误处理和测试是否符合设计。通过后才能复制该模式实现其余流程。

### G3：全功能完成

触发：四类物品流转和公益首版完成。

WorkerBuddy 必须停止并提交：

- 完整功能清单；
- 单元和集成测试报告；
- 数据库脚本；
- 已知问题；
- 设计偏差清单；
- 最新 commit。

Codex 执行设计符合性、安全、测试证据、可复现性和公网部署验收。

### G4：发布候选

触发：Codex 完成审计和受控修复。

输出：

- 验收报告；
- 缺陷关闭记录；
- 最终回归结果；
- 公网 smoke test；
- 已知限制；
- 发布建议。

用户批准后才能发布。

## 4. WorkerBuddy 的停止规则

到达 G1、G2、G3 或 G4 时，WorkerBuddy 立即停止新增功能和继续提交，并发送：

```text
GATE READY: <G1/G2/G3/G4>
Commit: <hash>
Scope completed: <本轮范围>
Evidence: <测试与文档路径>
Deviations: <无/列表>
Blocking questions: <无/列表>
Waiting for: Codex review / user decision
```

未收到明确通过前不得继续下一阶段。

## 5. Codex 修复边界

Codex 可以直接修复：

- 小范围路由或模板接线错误；
- 缺少权限校验；
- 跨校数据隔离遗漏；
- 状态或事务实现错误；
- R2、Vercel、Neon 适配问题；
- 小范围实现与详细设计不一致。

Codex 必须退回 WorkerBuddy 的情况：

- 缺少整个功能模块；
- 数据库结构需要重新设计；
- 需要变更业务规则；
- 需要新增核心依赖；
- 大范围架构重构；
- 测试证据不可信；
- 6.1/6.2 本身存在矛盾。

设计矛盾必须先更新设计和决策记录，再继续编码。

## 6. 测试证据

每次门禁至少保存：

- commit hash；
- Python 和依赖版本；
- 测试命令；
- 实际输出；
- 失败项与修复说明；
- 使用的数据库和环境；
- 页面截图或 smoke test 结果（适用时）。

测试通过结论以可复现证据为准，不以聊天中的口头声明为准。
