## 1. 执行摘要

“青禾流转”具有明确的校园生活场景和政策方向支持，但不属于必须建设的强制性信息化项目。项目采用 Flask、PostgreSQL、Flask-SQLAlchemy 和 Jinja2，核心技术均为成熟组件；单人、Web 端、4 周、无真实资金和运营商接口的设定在技术上是可行的。

项目的主要难点不是框架，而是多高校隔离、多流转模式下的业务状态一致性、学生名单认证模拟、权限控制、异常处理和文档工作量。建议采用“统一物品主模型、学校作用域隔离、分模式处理申请和履约、公益功能首版受限”的方式控制复杂度。

可行性结论为：**有条件可行，建议立项。**

## 2. 建设必要性

### 2.1 实际需求

校园内存在教材、宿舍用品、体育用品和学习用品的周期性闲置；同时存在学生临时使用、低价购买、免费领取和规范回收的需求。现有群聊和临时活动能够传播信息，但难以提供统一搜索、过程记录、状态追踪和责任确认。

### 2.2 政策与方向

官方政策持续鼓励绿色生活方式、循环经济、“互联网+二手”和“互联网+回收”，并明确鼓励学校开展旧书分享和旧书交换。政策与项目方向一致，但没有强制要求学校建设本平台，因此项目论证应侧重实际场景价值，而非政策合规义务。

### 2.3 课程价值

项目能够覆盖账号权限、业务规则、状态流转、事务一致性、异常处理、测试和部署等课程知识点，适合作为软件工程实践案例。

## 3. 备选方案比较

| 方案 | 说明 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 不建设 | 继续依赖群聊、公告和线下活动 | 零开发成本 | 无统一状态、无追踪、无法满足课程工程实践要求 | 不采用 |
| B. 直接使用商业二手平台 | 学生自行使用现有二手平台 | 上线快 | 不属于校园闭环，无法体现完整设计和数据治理，课程产出不足 | 不采用 |
| C. 开发单一二手商城 | 只做出售和购买 | 开发简单 | 无法覆盖借用、赠送、回收和公益，与同类学生项目同质化 | 不采用 |
| D. 开发校园综合物品流转平台 | 统一物品主模型并覆盖四类流转和受限公益 | 场景完整、课程价值较高、可公开展示 | 范围较大，需要严格控制状态和异常 | 采用 |

### 4.3 技术风险

1. 四类流转若各自维护一套物品和订单数据，会产生重复和状态冲突。应采用统一物品主记录，并明确同一时刻只允许一个进行中的流转业务。
2. 借用有归还，二手和赠送有成交或领取，回收有验收。不同业务的结束条件不同，不能依赖一个万能状态字段。
3. 图片上传会增加本地存储和 Cloudflare 迁移成本。图片不是首版核心时可以省略，或只使用虚构商品图片。
4. 真实支付、短信、实名、物流和公开募捐均不采用，因此外部接口风险基本为零。
5. 多高校支持不能让所有页面只靠前端过滤学校。学校作用域必须进入数据库关系、服务层权限和测试用例。
6. 学生名单导入包含姓名、电话、学号、年级、班级、专业和学院，属于敏感教育个人信息。课程版必须使用虚构名单，真实部署前需要学校授权和规范的数据保护措施。
7. PPT 没有规定业务表总数。数据设计将保留学校、校区、名单导入批次、状态历史、审计、回执等确有职责的实体，最终表数由 6.2 概念模型确定，不通过无意义拆表凑数。

### 4.4 Cloudflare 可行性

Cloudflare 不是课程必需项，但技术上具备可行性：

- Python Workers 当前支持 Flask/WSGI。
- PostgreSQL 可通过 Hyperdrive 连接，Neon、Supabase 都有官方示例。
- MySQL 也可通过 Hyperdrive 连接，但不是当前首选。
- 同步 SQLAlchemy 可使用，异步 SQLAlchemy 当前不支持。
- Cloudflare 不提供托管关系型数据库，需要另行准备公网 PostgreSQL 或 MySQL。
- Workers Free 方案每请求 CPU 时间为 10 ms，带鉴权和服务器端渲染的请求可能接近或超过该限制；稳定演示可能需要付费方案。
- 需要 `uv`、`pywrangler`/Wrangler、Cloudflare 账号以及 Workers 部署权限。
- 项目需设置 `compatibility_date` 不早于 `2026-09-08`，并启用 Python Workers 和 Hyperdrive 绑定。
- 图片头像、物品图片不能写入 Worker 本地磁盘；需要接 R2 或其他对象存储，或在展示版中只保留少量预置图片。
- 短信验证码和图片验证码均为模拟，不依赖真实运营商；Cloudflare 部署前只需保证模拟验证码在服务端可校验。

参考：

- Flask on Workers: https://developers.cloudflare.com/workers/languages/python/packages/flask/
- Hyperdrive for Python Workers: https://developers.cloudflare.com/hyperdrive/examples/python-workers/
- Workers Limits: https://developers.cloudflare.com/workers/platform/limits/

结论：首版以本地 Flask + PostgreSQL 验收。公网优先使用 Vercel + Neon PostgreSQL；若必须让应用运行在 Cloudflare，再增加 Hyperdrive、R2、Node/uv 和部署调试，预计额外 1–2 个工作日。

### 4.5 公网数据库方案比较

数据库限制解除后，PostgreSQL 比继续寻找免费 MySQL 更合适。当前可优先比较：

| 方案 | 当前免费额度 | 闲置与计费 | 与 Cloudflare 的兼容性 | 适用结论 |
|---|---|---|---|---|
| Neon PostgreSQL | 100 个项目；每项目每月 100 CU-hours、1 GB 存储、5 GB 公网流量；无需信用卡 | 不因项目闲置暂停；计算空闲 5 分钟后缩到零，下次查询自动唤醒 | 官方 Hyperdrive 示例支持 | 首选 |
| Supabase PostgreSQL | 500 MB 数据库、1 GB 存储、5 GB egress、2 个活跃项目 | 项目连续 1 周无活动后暂停；免费版无自动备份/PITR | 官方 Hyperdrive 示例支持 | 需要 Supabase Auth/Storage 时选择 |
| TiDB Cloud Starter | 每月 5 GiB 行存、5000 万 RU；无需信用卡 | 免费额度内 0 元 | MySQL-compatible，但无专项 Provider 示例 | 只有在坚持 MySQL 兼容写法时选择 |
| 本机 MySQL/PostgreSQL | 0 元 | 本机关机即无法公网访问 | 不可直接作为公网数据库 | 仅用于本地开发与课程验收 |

本项目当前选择：

- 本地：PostgreSQL 18。
- 公网：优先 Neon PostgreSQL。
- 应用入口：Vercel Flask/WSGI 为首选；Cloudflare Workers + Hyperdrive 为第二阶段备选。
- 文件：Cloudflare R2 或 Vercel Blob 二选一。

参考：

- Neon Pricing: https://neon.com/pricing
- Neon Plans: https://neon.com/docs/introduction/plans
- Cloudflare Neon + Hyperdrive: https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/neon/
- Supabase Pricing: https://supabase.com/pricing
- Cloudflare Supabase + Hyperdrive: https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/supabase/

## 5. 业务可行性

### 5.1 可统一的部分

- 用户、角色和权限。
- 物品基本信息、分类、成色和图片。
- 物品当前流转方式与业务状态。
- 交接码、地点、时间和操作记录。
- 争议、审核和管理员处理。
- 公益项目、实物捐赠与回执。

### 5.2 不能强行统一的部分

- 借用强调归还、逾期和物品验收。
- 二手强调价格、模拟支付和成交确认。
- 赠送强调申请、领取和完成。
- 回收强调回收点接收和绿色贡献记录。
- 公益捐赠强调募集目标、物资核验和回执。

因此，业务模型可以采用共享主记录，但每类流转需要独立的业务规则与结束条件。

### 5.3 单人范围建议

首版必须优先完成一条端到端闭环，再扩展其他模式。推荐的开发顺序是：

1. 物品发布和状态展示。
2. 共享借还与归还。
3. 二手交易和赠送。
4. 绿色回收。
5. 公益实物捐赠、项目进度和回执。

不建议四类流转同时从零开始，否则容易形成多套半成品。

## 6. 经济可行性

### 6.1 直接成本

| 项目 | 预计成本 |
|---|---:|
| Python、Flask、PostgreSQL、Git | 0 元 |
| 本地开发和测试 | 0 元 |
| GitHub 公共仓库 | 0 元 |
| 原型和图表工具 | 0 元 |
| 域名 | 可选，不在首版预算 |
| Cloudflare Workers | 可选；免费方案有限制，稳定运行可能产生月费 |
| 公网数据库 | 首选 Neon PostgreSQL 免费层；Supabase 为备选 |

### 6.2 时间成本

按单人、4 周、每天 5–7 小时的有效投入估算：

- 需求与设计文档：5.5 个工作日。
- 核心开发和联调：11 个工作日。
- 测试、缺陷修复和交付文档：2.5 个工作日。
- 预留缓冲：2 个工作日。

总工作量约 105–147 小时。若实际每天投入低于 5 小时，应把周期延长到 5 周，或将 Cloudflare、图片上传等增强项移出首版。

### 6.3 收益

- 课程：形成可验收的完整项目、阶段文档和测试证据。
- 作品集：可展示多角色、状态机、权限、异常流程和数据设计能力。
- 实践：可用于校园小范围试用。
- 公益：可展示物资捐赠和回执链路，但不得夸大为真实公益成果。

## 7. 组织与操作可行性

### 7.1 人员

开发与文档均由单人完成，建议设置三种外部检查角色：

- 教师：审核范围、文档和课程要求。
- 测试同学：按用例体验主流程。
- 代码/文档审阅者：检查 README、数据安全和公开内容。

### 7.2 开发方式

采用增量交付：

- 每个阶段结束时保留可运行版本。
- 每个阶段同步更新文档和测试。
- 新需求先进入变更清单，不直接插入当前阶段。
- 每个增量至少完成一次真实运行验证。

### 7.3 运维

课程首版按单实例部署，不承诺高可用。数据库备份、日志审计和故障恢复以本地演示和 GitHub 可复现为目标，不建设生产级运维体系。

## 8. 法律、伦理与安全可行性

### 8.1 支付

不接真实支付。二手交易仅记录模拟支付状态，避免支付通道资质、回调验签、资金结算和退款风险。

### 8.2 公益

《中华人民共和国慈善法》规定，公开募捐需要相应资格，义卖属于公开募捐方式之一；无资格组织或个人需与具有资格的慈善组织合作。首版公益功能仅做：

- 实物捐赠递交。
- 公益项目目标和数量进度。
- 物资接收回执公示。

首版不接受真实资金、不做真实公益义卖、不对外宣称已经帮助特定儿童。

若未来接入真实公益，应另行完成：

- 合作机构资质核验。
- 物资安全、卫生和适用性审核。
- 捐赠协议和回执管理。
- 公开募捐方案及备案判断。
- 财务与个人信息保护评估。

### 8.3 个人信息

- 只收集完成业务必需的信息。
- 不展示受助儿童个人身份、联系方式、家庭地址和可识别照片。
- 测试和公开仓库使用虚构数据。
- 数据库密码和部署密钥不得提交到 GitHub。
- 学生名单导入必须记录导入批次、操作人和源文件摘要，避免无法追溯的覆盖导入。
- 注册时仅使用名单中的学号、手机号和必要身份字段进行匹配；错误提示不得泄露完整名单信息。
- 头像上传需限制格式、大小和访问权限，防止恶意文件和隐私泄露。

### 8.4 平台内容

禁止发布违法、危险、侵权和不适合校园流转的物品。管理员需要具备下架、封禁和争议处理能力。该规则的具体功能属于需求分析阶段。

## 9. 进度可行性

### 9.1 基准假设

- 开始日期为 2026-11-18，目标截止日期为 2026-12-16。
- 计划周期为 21 个工作日。
- 每天有效投入 5–7 小时。
- 每 3 个工作日形成一个可运行检查点。
- 周末原则上不作为固定开发日；12 月 12–13 日和 12 月 15–16 日作为最终修复与交付缓冲。

### 9.2 有条件可行的原因

以下条件同时满足时，进度可行：

1. 不加入真实支付、短信、物流、实名认证和真实募捐。
2. 公益义卖不进入首版开发。
3. 四类物品流转复用统一物品主记录，不重复建设四套商城。
4. 图片和头像使用受控本地上传或 R2，不在核心阶段阻塞开发。
5. 多高校只做逻辑隔离和预置/导入名单，不接全国高校真实认证接口。
6. 文档与开发同步进行。

### 9.3 不可行条件

出现以下任一条件时，原计划不可行：

1. 要求复制企业完整商城功能，或新增超出当前范围且需要重新估算工期的硬指标。
2. 要求真实支付、订单结算和退款。
3. 要求真实公益募资与资金采购闭环。
4. 要求同时交付 Web、小程序和 App。
5. 2 周内从零完成全部四类流转、认证模拟、多校区隔离和四个公益子模块。

## 11. 可行性结论

### 11.1 结论

**有条件可行，建议立项。**

### 11.2 必须满足的条件

1. 首版采用明确的范围冻结。
2. 公益义卖与真实公益资金不进入首版代码。
3. 物品流转以一套主模型为核心，避免重复建设。
4. 项目按 4 周、21 个工作日和每天 5–7 小时执行。
5. 多高校仅做逻辑隔离、预置学校和虚构名单，不接真实学校认证。
6. 以本地可运行和可复现为首要交付标准，Cloudflare 和图片上传作为增强项。

### 11.3 建议决策

批准问题定义、可行性结论和开发计划后，再进入 6.1 需求分析。未获得批准前，不建立项目脚手架、不创建数据库表、不编写业务代码。
