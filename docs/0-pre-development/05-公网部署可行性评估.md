## 1. 结论

可以使用大厂免费资源完成公网展示，但不建议把 Cloudflare、Supabase 和 Vercel 全部叠加。

推荐顺序：

1. **公网部署最简单的 MySQL 路线：Vercel + TiDB Cloud Starter + Cloudflare R2**
2. **Cloudflare 一体化路线：Cloudflare Workers + TiDB Cloud Starter/Aiven MySQL + R2**
3. **允许改用 PostgreSQL 时才考虑：Vercel 或 Cloudflare + Supabase**
4. **不推荐：Cloudflare + Supabase + Vercel 三平台全套叠加**

项目验收仍以本地 Flask + MySQL 为准。公网部署是展示增强项，不能成为 12 月 16 日交付的阻塞条件。

## 2. 硬约束

### 2.1 数据库

- 项目要求 MySQL。
- Supabase 的核心数据库是 PostgreSQL，不提供托管 MySQL。
- Supabase 即使存在 MySQL Foreign Data Wrapper，也是让 PostgreSQL 读取外部 MySQL，不是把 Supabase 当 MySQL 数据库。
- 因此 Supabase 不能直接替换本项目的 MySQL。

### 2.2 应用

- 项目使用 Flask + Jinja2 服务端渲染。
- Vercel 当前支持 Flask/WSGI 应用。
- Cloudflare Python Workers 当前支持 Flask/WSGI。
- 公网部署不应迫使项目改为 React 前后端分离或原生 App。

### 2.3 文件

- 物品图片和用户头像需要持久化对象存储。
- Vercel 与 Cloudflare Functions 的运行环境不适合依赖本地持久磁盘。
- Cloudflare R2 免费额度较宽，且与 Cloudflare 集成简单。

## 4. 平台组合评估

### 4.1 Vercel + TiDB + R2

```text
浏览器
  → Vercel（Flask / Jinja2 / WSGI）
  → TiDB Cloud Starter（MySQL-compatible）
  → Cloudflare R2（头像和物品图片）
```

优点：

- Flask 有官方 Vercel Python 运行时支持。
- 无需改写为前后端分离。
- 300 秒函数时长对普通 Web 请求足够。
- 无需 Hyperdrive 和 Python Workers 兼容日期。
- TiDB 免费额度适合教学项目。
- R2 免费 10 GB，且公网出口免费。

风险：

- TiDB 是 MySQL-compatible，不是官方 Oracle MySQL。
- Vercel 函数是短生命周期运行环境，数据库连接池和连接复用需要验证。
- Vercel 函数请求/响应体约 4.5 MB，图片不能直接大文件上传。
- Vercel 应用和 TiDB 可能不在同一区域，会有额外延迟。

适用判断：

- 这是最简单的公网部署路线。
- 若 Vercel 连接 TiDB 成功，可作为首选展示方案。

### 4.2 Cloudflare Workers + TiDB/Aiven + R2

```text
浏览器
  → Cloudflare Workers（Flask / Jinja2 / WSGI）
  → Hyperdrive
  → TiDB Cloud Starter 或 Aiven MySQL
  → R2（头像和物品图片）
```

优点：

- 应用、连接池、文件和 CDN 都在 Cloudflare。
- Hyperdrive 免费额度为每天 100,000 次数据库操作。
- R2 与 Worker 配合自然，图片可通过 R2 提供。
- Cloudflare 提供 Workers 与 Supabase、PlanetScale、RDS 等数据库的集成文档。

风险：

- Free Workers 每个请求只有 10 ms CPU，鉴权和 SSR 可能超标。
- Python Workers、Flask、Hyperdrive、TiDB/Aiven 是新组合，需要先做最小 PoC。
- 需要 `uv`、`pywrangler`/Wrangler 和 R2 配置。
- Workers 免费 CPU 限制比 Vercel 函数更容易影响页面渲染。

适用判断：

- 如果最终以 Cloudflare 为唯一部署平台，选择此路线。
- 不适合作为第一个公网部署实验，应先完成本地验收或 Vercel PoC。

### 4.3 Vercel + Supabase + R2

只有当数据库约束允许把 MySQL 改成 PostgreSQL 时才成立。

如果仍坚持 MySQL：

- 不能用 Supabase 主数据库。
- 用 Supabase 只做文件存储或认证，会把用户、认证和业务数据拆成两套系统。
- 自定义学生名单核验、模拟短信验证码和三级角色会与本项目认证逻辑重复。

因此当前不采用 Supabase 作为数据库。

### 4.4 Cloudflare + Supabase

Cloudflare 有官方 Supabase + Hyperdrive 文档，技术上可行，但 Supabase 是 PostgreSQL。

该方案适合允许使用 PostgreSQL 的版本，不适合当前 MySQL 约束。

### 4.5 Cloudflare + Supabase + Vercel

不推荐：

- Vercel 负责应用、Supabase 负责 PostgreSQL、Cloudflare 负责 R2/代理，会增加三套账号、三套配置和三套故障点。
- 数据库仍不符合 MySQL 要求。
- 学生名单、登录会话和图片访问要跨平台排查。
- 单人 21 个工作日项目没有足够时间维护这种混合架构。

## 5. 推荐结论

### 5.1 项目验收

使用本地 Flask + MySQL 8.4（兼容 MySQL 8.0 写法）+ pytest + Jinja2，完成四类物品流转、认证模拟和公益首版。

### 5.2 公网展示首选

先尝试：

```text
Vercel + TiDB Cloud Starter + Cloudflare R2
```

理由：

- 保留 Flask/Jinja2。
- 保留 MySQL-compatible 数据访问方式。
- 不需要把业务改成 React。
- 不需要提前承担 Cloudflare Workers 10 ms CPU 风险。
- 免费额度足够完成运行演示。

### 5.3 Cloudflare 专属展示

如果 Vercel 路线成功且仍有时间，再做：

```text
Cloudflare Workers + Hyperdrive + TiDB/Aiven + R2
```

若 Workers 免费 CPU 限制导致请求失败，再判断是否需要 Workers Paid。

## 6. 部署前必须验证的 PoC

1. 创建 TiDB Cloud Starter MySQL-compatible 实例。
2. 导入 `schema.sql` 和虚构种子数据。
3. 从 Vercel Python Function 使用 PyMySQL 连接 TiDB。
4. 验证 TLS、连接池、冷启动和请求超时。
5. 验证 Vercel 上 Jinja2 模板和静态资源加载。
6. 验证 R2 图片上传和公网读取。
7. 验证多高校隔离在学生名单、物品、回收和公益接口中生效。
8. 若转 Cloudflare，再验证 Hyperdrive、Python Workers 和 R2。

## 7. 不采用的方案

- 不把 Supabase 当 MySQL。
- 不为了部署把服务端模板强制改造成 React SPA。
- 不同时维护 Vercel 和 Cloudflare 两套应用入口。
- 不把 R2、Supabase Storage 和 Vercel Blob 三套文件存储同时接入。
- 不在项目验收前用真实学生名单或真实公益资金做部署测试。
