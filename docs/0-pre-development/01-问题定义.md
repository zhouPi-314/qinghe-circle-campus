## 1. 文档目的

本文档用于回答三个前置问题：

1. 为什么需要建设“青禾流转”。
2. 项目要解决的核心问题是什么。
3. 项目的目标、边界和成功条件是什么。

本文档不展开用例清单、页面清单、数据表、接口、模块代码等需求分析内容。上述内容应在问题定义获批后，再按课程 6.1 阶段开展。

## 2. 项目概述

“青禾流转”是一个仅在 Web 端运行的校园物品循环平台。平台把原本分散在群聊、公告栏、线下跳蚤市场和校园回收活动中的物品流转行为，组织为一条状态可追踪、责任可确认的数字化流程。

平台采用多高校逻辑隔离设计：同一套系统未来可以承载多所学校，但单个用户只能进入自己所属学校的业务区域，物品、公益项目、回收点和管理员权限均不得跨校共享。首版不接入真实全国高校认证接口，只使用导入或预置的高校与学生名单进行模拟。

平台围绕物品的四类流转方式展开：

- 共享借还。
- 二手交易。
- 免费赠送。
- 绿色回收。

在上述物品流转基础上，首版增加受控的公益板块，包括：

- 书籍等实物的公益捐赠。
- 公益项目目标与募集进度。
- 物资接收后的回执公示。

“公益义卖”和“微心愿项目使用虚拟公益金额认领”纳入总体设计，但不进入首版开发范围。

## 3. 开发背景

### 3.1 校园生活中的实际问题

高校学生在入学、换课、毕业和搬寝等周期中，会产生大量闲置物品，例如教材、课外书、文具、宿舍用品、小型电子产品、体育用品和生活用品。这些物品常面临以下问题：

1. **供需分散**：转让信息散落在多个聊天群、朋友圈和临时活动中，学生难以搜索和跟踪。
2. **一次性拥有成本高**：部分物品只在短时间使用，全部购买会造成不必要支出和宿舍堆积。
3. **流转过程缺少凭证**：借出、归还、交付和领取多依赖口头约定，逾期、损坏和争议难以追溯。
4. **二手、借用、赠送和回收彼此割裂**：同一物品在不同渠道重复发布，状态容易冲突。
5. **公益捐赠去向不清晰**：学生难以确认捐出的书籍和物资是否被接收、整理和送达，容易产生信任问题。
6. **绿色行为难以积累和展示**：旧书交换、闲置再利用和回收行为缺少统一记录，校园绿色实践难以形成持续机制。

### 3.2 政策背景

项目方向与以下官方政策具有一致性。政策提供方向性依据，不构成对具体平台的强制建设要求。

1. 《中共中央关于制定国民经济和社会发展第十五个五年规划的建议》提出“深入推进数字中国建设”，并要求加快形成绿色生产生活方式、提高垃圾分类和资源化利用水平、促进循环经济发展、健全绿色消费激励机制。[1]
2. 2026 年政府工作报告在介绍“十五五”规划纲要草案主要任务时，继续强调数字中国建设、绿色生产生活方式和碳达峰目标。[2]
3. 《“十五五”碳达峰行动方案》明确提出发挥循环经济助力降碳作用，完善废旧物资回收网络，推广“互联网+”回收模式，畅通“换新+回收”渠道。[3]
4. 《国务院办公厅关于加快构建废弃物循环利用体系的意见》鼓励“互联网+二手”和“互联网+回收”，强调二手交易的便利化、规范化和信息追溯。[4]
5. 《关于加快废旧物资循环利用体系建设的指导意见》明确提出鼓励各级学校设置旧书分享角、分享日，促进师生旧书交换使用。[5]
6. 《关于加快推进废旧纺织品循环利用的实施意见》提出打通回收设施“进校园”的壁垒，并探索毕业季进校园等回收模式。[6]

这些政策说明“互联网+二手”“互联网+回收”、校园旧书循环和绿色生活方式具有现实政策支持，但不能据此宣称政策要求每所高校开发本平台。

### 3.3 课程背景

本项目同时承担课程实践任务。课程样例采用 Flask、MySQL、Flask-SQLAlchemy 和 Jinja2 服务端渲染；当前课程不要求必须使用 MySQL，项目保留 Flask、Flask-SQLAlchemy 和 Jinja2，数据库在 PostgreSQL 等关系型数据库中选型。课程强调：

- 明确的项目边界。
- 正常流程与异常流程闭环。
- 页面、规则和数据库记录一致。
- 身份、权限、状态和金额规则不能只依赖前端。
- 测试结果和交付结论有证据。
- 其他学习者可以按说明重新启动系统。

因此，本项目不能只做物品列表和后台增删改查，需要选择一条具有真实状态变化、责任交接和可验证结果的校园业务链路。

## 4. 核心问题定义

原有“二手交易系统”或“共享物品系统”通常只覆盖一种流转关系，无法处理同一物品在可借、可售、可赠和待回收之间的状态变化。若简单叠加多个商城，又会出现数据重复、状态冲突和操作责任不清。

本项目的核心问题是：

> 如何在不引入真实支付、短信、物流和政府数据接口的前提下，建立一个面向校园的可信物品流转系统，使一件物品在多类流转方式之间保持清晰、互斥、可追踪的状态，并为校园公益物资捐赠提供有来源、有进度、有回执的闭环？

该问题包含三个层面：

1. **业务层**：同一物品如何选择并完成借用、出售、赠送或回收。
2. **治理层**：身份、权限、审核、交接、逾期、争议和审计如何得到控制。
3. **公益层**：实物捐赠与公益项目如何记录、核验、公开进度并证明物资去向。

## 5. 项目目标

### 5.1 业务目标

1. 为校园闲置物品提供一个集中、可搜索、可追踪的流转入口。
2. 支持借还、二手、赠送和回收等不同流转方式，并保证同一物品当前业务状态互斥。
3. 通过交接凭证、状态记录和双方确认降低口头约定的不确定性。
4. 为首版公益板块提供实物捐赠、募集进度和回执公示能力。

### 5.2 教学目标

1. 完整体现需求分析、概要设计、增量开发、测试和交付的软件工程过程。
2. 展示多角色权限、业务状态机、数据一致性、异常流程和测试证据。
3. 形成可公开到 GitHub 的作品，但不以真实商业运营为验收条件。

### 5.3 绿色与公益目标

1. 通过再次使用减少可继续使用物品的直接废弃。
2. 提高校园旧书、学习用品和生活物品的再利用率。
3. 让公益物资的需求、募集、核验和回执均可查询。
4. 不以夸大的环保减排数字或未经证实的公益成果作为宣传依据。

## 6. 主要利益相关者

| 利益相关者 | 关注点 |
|---|---|
| 普通学生用户 | 物品是否可用、如何申请、何时交接、流转是否可信 |
| 物品发布者/所有者 | 物品状态、申请人、交接和归还结果、是否发生损坏或争议 |
| 物品借用者/购买者/领取者 | 信息真实性、履行约定、取消、退款模拟和反馈 |
| 校园回收点/公益物资接收点管理员 | 物品验收、入库、募集数量、物资整理和回执登记 |
| 平台管理员 | 用户权限、内容审核、异常处理、争议处理和数据安全 |
| 课程教师 | 文档质量、过程可追踪、系统可运行、测试充分 |
| 项目开发者 | 范围可控、单人可在有限周期完成、技术风险可管理 |

## 7. 初步范围边界

### 7.1 首版纳入范围

1. 物品发布、浏览和状态管理。
2. 共享借还、二手交易、免费赠送、绿色回收四类流转。
3. 校内交接、归还、取消、逾期和基础争议记录。
4. 基础账号、角色和权限控制。
5. 书籍等实物的公益捐赠。
6. 公益项目目标、募集数量和完成进度。
7. 物资接收后的回执与公示。
8. 完整的启动说明、SQL 脚本、测试记录和阶段文档。
9. 多高校数据逻辑隔离，用户只能在本校范围内开展业务。
10. 学生名单导入与注册核验的教学模拟。
11. 普通用户、回收/公益点管理员、平台管理员三类可见角色。
12. 学生昵称、头像和角色标签展示。
13. 基础响应式页面。
14. 在技术可行时支持物品图片上传。
15. 同一学校内部允许多个校区之间流转，跨学校不允许。

### 7.2 纳入设计但暂不开发

1. 公益义卖。
2. 使用虚拟公益金额认领微心愿。
3. 更复杂的公益金流水和采购记录。

暂不开发的功能必须写入 6.1 和 6.2 的范围说明与后续规划，不应在首版页面中放置无功能的占位按钮。

### 7.3 明确排除

1. 真实支付、真实资金托管、自动退款和结算。
2. 短信、邮件、运营商通道和实名身份接口。
3. 真实公开募捐、真实公益资金代收和采购。
4. 实时聊天、即时语音、视频和直播。
5. 地图导航、骑手调度、真实物流和快递面单。
6. 推荐算法、AI 定价、图像识别和智能审核。
7. 移动 App、微信小程序和多端原生客户端。
8. 面向全社会的商业交易平台。
9. 大规模微服务、消息队列和分布式事务。

## 8. 成功标准

项目达到以下条件，方可认为问题定义得到有效回应：

1. 一件物品可以完成至少一种从发布到结束的完整流转。
2. 借用、出售、赠送和回收之间存在互斥规则，不产生相互冲突的进行中业务。
3. 关键操作能够追溯到用户、时间和业务状态。
4. 借还、交接、逾期、取消和争议至少具备基本异常路径。
5. 公益实物捐赠可以形成“需求—募集—核验—回执—公示”的可查询链路。
6. 普通用户、物品所有者和管理员之间的权限边界明确。
7. 系统在本地环境中可按 README 重新启动，并能使用种子数据完成演示。
8. 核心流程、异常分支和权限边界有测试用例及实际结果。
9. GitHub 仓库不包含密码、密钥、真实个人信息或未授权素材。

## 9. 约束与假设

1. 开发人员为单人。
2. 项目从 2026-11-18 开始，目标截止日期为 2026-12-16，共约 4 个自然周、21 个工作日。
3. 每天计划有效投入 5–7 小时。
4. 技术主线以 Flask、Flask-SQLAlchemy 和 Jinja2 为准；数据库优先使用本地 PostgreSQL 18，公网优先使用 Neon PostgreSQL，最终以 6.2 设计冻结结果为准。
5. 项目为 Web 端，默认优先桌面浏览器，同时保证基础移动网页可用。
6. 预算按个人学习账号和本地环境控制，不购买商业服务也可完成课程验收。
7. 课程验收以本地运行为主；Cloudflare 部署作为期望完成但不阻塞课程验收的公网展示目标。
8. 支付、短信、公益金和公益义卖均为教学模拟或后续规划。
9. 首版不追求真实商业运营指标，重点验证业务闭环和软件工程过程。
10. PPT 没有规定业务表总数；最终表数由 6.2 概念数据模型和实体关系确定，不预设固定数字。
11. GitHub 仓库先保持私有，在首个可运行版本或 M0 批准后转为公开。
12. 首版不依赖真实外部用户测试，以预置数据和用例演示作为验收依据。
13. 同校不同校区允许流转，学生和管理员仍限定在本校范围内。
14. 首版共设置 2 个管理员测试账号：1 个回收/公益点管理员、1 个平台管理员。
15. 课程最终包含答辩或现场演示准备。

## 10. 主要风险

| 风险 | 影响 | 初步应对 |
|---|---|---|
| 共享、二手、赠送、回收四种模式同时开发导致范围膨胀 | 核心流程无法按时完成 | 统一物品主模型，但分期实现；优先完成一条完整链路 |
| 6.2 概念建模遗漏实体职责或过度拆表 | 数据库返工、关联复杂或测试成本增加 | 用 ER 图、关系基数和数据字典审核，不以固定表数驱动设计 |
| 多高校数据越权 | 用户看到其他学校物品或学生名单 | 所有业务数据绑定学校标识，服务层统一校验学校范围 |
| 学生名单包含姓名、手机号、学号等个人信息 | 数据泄露、冒领注册和隐私风险 | 课程版只使用虚构名单；真实导入前需学校授权、最小化和加密保护 |
| 公益功能被误解为真实募捐或真实资金管理 | 合规和声誉风险 | 首版仅做实物登记、模拟数据和回执，不接受真实资金 |
| 借用、交易和回收状态互相污染 | 数据不一致 | 在 6.2 阶段明确状态边界和互斥规则 |
| 图片和附件依赖公网存储 | Cloudflare 部署复杂、成本增加 | 图片非核心时可省略；需要时再确定本地或对象存储策略 |
| 单人同时承担开发与文档 | 测试和文档被压缩 | 每个增量同步更新文档和测试，不堆到最后 |
| GitHub 公开真实用户数据 | 隐私与安全问题 | 只使用虚构测试数据和脱敏截图 |
